## The one thing to check first

**Three changes are deployed and none of them has been observed working yet.**
The farm auto-updates on a 6-hour cadence (`normalCheckEvery`, jittered), and
v0.1.70 landed at 17:42Z and v0.1.71 at ~19:00Z. Until the farm picks them up,
the D axis is moving on ordinary `csx run` traffic and nothing else.

Two queries decide it, and they are the only honest signal:

```sql
-- v0.1.70: does a verification report the tree it resolved?
-- A verification's batches carry the sample digest as the project bucket:
-- 64 hex characters. An ordinary csx run bucket is 12.
SELECT count(*) FROM dependency_edge WHERE length(bucket) = 64;

-- v0.1.71: does a resolution that found nothing get recorded?
SELECT count(*) FROM dependency_resolution;
```

Both were **0** at 19:05Z. If they are still 0 after the farm has verified for
a day, the edges are being produced and dropped somewhere between the verifier
and the store — that is the refutation condition written into #87, and it is
the first thing to investigate rather than assume.

Do not read a rising `dependencyGraph` as proof. It rose from 575 to 591 during
this session with **zero** verification-derived edges; that was user traffic.
This mistake was made once already in this session and corrected.

## Open work, in the order it matters

### 1. PR #135 — the Python lane (ready, needs merge + tag)

The Linux Python lane ran `python:3.12-alpine`. musl cannot use a manylinux
wheel, so a project that publishes manylinux only falls back to an sdist build
that image has no toolchain for. Nine defect reports named it. Confirmed in a
container:

```
python:3.12-alpine   llvmlite==0.44.0 -> Failed to build installable wheels
python:3.12-slim     llvmlite==0.44.0 -> IMPORT OK 0.44.0
```

The break is narrower than "C extensions", and it is worth stating precisely
because the first version of this claim was too broad: `numpy`, `lxml` and
`pyarrow` all install on Alpine — they publish musllinux wheels too. The rule
is "no musllinux wheel", and llvmlite is that case.

Every pypi receipt in production carries `libc: musl` — 510 of them, not one
glibc. The evidence was honest; it was also the only Python environment this
network had ever measured.

The musl registry entries stay and are simply no longer selected: 510 receipts
name them and must keep resolving. A test pins that.

**After merging this, a new tag is needed** — the lane lives in the verifier.

### 5. #130 — Windows is only tested at release

```
ci.yml      (pull_request)   runs-on: ubuntu-latest
release.yml  windows-test    runs-on: windows-latest
```

A change to daemon listeners, named pipes, process spawning or path handling
gets no Windows signal until a tag is cut — and the tag is what fails closed.
This cost one full investigation this session: the v0.1.70 release stopped on
`TestDaemonListenerNeverBindsAnAddressTheFirewallWouldPromptFor/after_upgrade`
("daemon did not shut down", 10s budget), which re-ran unchanged and passed.

Evidence it was not the change in that release: the daemon listener change is a
no-op when the port is free and every test home sets `DaemonPort = 0`; the new
tests are in `homeisolation_test.go`, which sorts after `firewallprompt_test.go`
and therefore runs later; the test dates from 6d0f0da, five releases earlier.
Not reproduced locally in 10+ runs including under `GOMAXPROCS=2`.

### 6. The dependency map's remaining half

v0.1.70 fills D wherever a sample exists (`SE-`, 1,283). v0.1.71 fills the
leaves (~490). Neither reaches `-E-` coordinates that have no sample and are
not inside anyone else's resolved tree.

The queue cannot bootstrap those: the `DEPENDENCY` branch of
`authoringCoverageCTE` reads from `dependency_closure`, which is derived from
`dependency_edge` — it walks an existing graph rather than creating one. Every
work kind's deliverable is a sample.

What is missing is a work kind whose deliverable is a resolved tree: resolve
`pkg@version` in an empty directory, read the lockfile, report the edges. No
contract, no container build. That is also the open half of #87.

## Things worth knowing before touching this code

- **A fixture shorter than production is how the two worst bugs of this session
  hid.** The receipt backfill lost all 9,883 observations to a project bucket
  71 bytes long against a 64-byte limit, because the test used a short id. The
  same shape recurred here: `TreeBatches` produced batches the server refused
  with `environment.schemaVersion must be 1, got 0`, and the leaf claim was
  silently never made because the lockfile fixture carried no registry artifact
  URL and no installed tree. Put the real thing through the real validator.
- **The fake and PostgreSQL must not diverge**, and a green suite cannot show
  it. `dependency_edge` had no PG integration coverage at all before this
  session — the one row the whole dependency effort exists to create was
  untested in its production implementation.
- **Verify by rendering, not by reading.** The ad landed inside a finding card
  with the markup and CSS both exactly as written; only a screenshot showed it.
  The snippet relocates itself unless `[data-adisad-slot]` is present.
- **`.home-ad` is on a public ad-blocker filter list.** The home ad renders for
  visitors without a blocker and is hidden for those with one. Confirmed by
  control: `ad-banner`, `sponsored-content`, `adisad-unit` and
  `aria-label="Advertisement"` all render; only `home-ad` is hidden. Renaming
  it would work and would be circumventing a blocker the visitor installed —
  left as the user's call, still unanswered.
