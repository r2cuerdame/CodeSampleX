# Handoff — 2026-08-30

Where things stand, what is proven, what is merely deployed, and what to check
first. Written at the point of switching agents; nothing here is a plan, only
state and the evidence for it.

## The one thing to check first

**The farm is running at a sixth of its throughput, and that now gates every
other answer.** Three authoring assignments an hour across three slots, all of
kind WANTED, one hour with none at all. No pypi verification has run since
19:27Z — before the Python lane fix shipped — so the lane cannot be validated,
new defect reports cannot arrive, and the dependency map fills six times slower
than it should.

That is #136, and the server side is fully ruled out: 322 unanswered EXPANSION
candidates in npm and golang, 1,366 coverage holes, 0 assignments blocking the
window, 53 quarantined coordinates with none new, a 30ms claim endpoint, and a
worker script unchanged since 2026-08-29 whose loop is `while true`. The farm
node is where the answer is and it is not reachable from here.

Two experiments settle it, both in #136:

1. Pin one slot to the **v0.1.69** binary, leave the others on current, compare
   assignments per service start over an hour. That confirms or clears the
   version boundary the reporter measured.
2. Check whether the systemd unit runs the worker `.sh` **as a file or piped
   into a shell**. Piped, any child that consumes stdin ends the script at EOF
   — which exits 0 after one iteration and matches every symptom.

## Open work, in the order it matters

### 1. #136 — the farm runs at a sixth of its throughput

The top of this document. Everything else in this list is slower or
unmeasurable until it is resolved, and the answer is on the farm node.

### 2. #129 — prove the daemon fix restored evidence drain

The farm reported all four homes showing identical numbers (28/14 hits, 6 known
packages, 0 batches). That was one daemon answering for all of them; three homes
had none, so their upload loops never ran. Fixed in v0.1.70 and not yet
confirmed, because #136 leaves almost nothing running to measure.

`Automatic evidence sent` moving off 0, per home, is the answer. If it stays 0
with the farm healthy, the recording path is a separate problem and the daemon
fix was not the whole cause.

Ruled out already, with evidence: nothing gates recording on `InitAt`;
`run_observed_command` records directly through `RecordCommandOutput` and needs
no daemon; no upgrade path discards a store — `Home()` is `$CSX_HOME` or
`~/.csx` with no migration, `config.Load` never rewrites, and the updater
removes only staged binaries and locks.

### 3. The defect channel is empty on purpose

All 18 reports were cleared after v0.1.74 shipped. `RecordCSXIssueReport`
dedupes on `ON CONFLICT (fingerprint)` and never looks at the verdict, so a
report of a fixed defect would have bumped a counter on the old row instead of
arriving as a new one. The full ledger is preserved as a comment on PR #133.

Of what was in it: ten closed against GH-134 (the Alpine/musl lane), three
fixed in #138, three fixed in #141 and #142, and **two never explained** —
reports 3 and 4, a deploy-oriented search returning pytest, Express and certifi
because generic symbol subtokens counted as named-subject relevance. There is
suppression on that path already (`suppressedReason: unrelated-ecosystem` is
observable), so what is open is whether the named-subject signal is too loose.

Nothing has arrived since the clear, which is #136 again: no work, no builds,
nothing to report.

### 4. #125 — one Go release counted twice

`pgx/v5@v5.10.0` and `@5.10.0` are separate rows. `ParsePURL` stores the version
verbatim and `PURL.Major()` already compensates for the missing prefix at
shard-key time, which is the codebase knowing both shapes exist. Normalising at
parse time changes stored keys, so it needs the normalisation and a migration
that folds existing rows in the same release.

### 5. #130 — Windows CI, half closed

Windows now runs on every merge to main (#140), which is what made the process
tree work in #141 possible: it is platform-specific code that would otherwise
have been first exercised by a tag.

Still open: the daemon shutdown flake that blocked v0.1.70. It was not fixed —
`Run` bounds its own `srv.Shutdown` at 5s and its only other work is three
`os.Remove` defers, so no path in the code takes ten seconds, and it has not
reproduced locally standalone, under `GOMAXPROCS=2`, or across ten sweeps. A fix
guessed against a failure that rare is a fix nobody can check. The budget was
left alone and the failure made diagnosable instead: it now prints how long the
cancel had been pending and dumps every goroutine, so the next occurrence names
what held it.

### 6. The dependency map's remaining half

v0.1.70 fills D wherever a sample exists (`SE-`, 1,283). v0.1.71 fills the
leaves (~490). Neither reaches `-E-` coordinates that have no sample and are
not inside anyone else's resolved tree.

The queue cannot bootstrap those: the `DEPENDENCY` branch of
`authoringCoverageCTE` reads from `dependency_closure`, which is derived from
`dependency_edge` — it walks an existing graph rather than creating one. Every
work kind's deliverable is a sample.

What is missing is a work kind whose deliverable is a resolved tree: resolve
`pkg@version` in an empty directory, read the lockfile, report the edges. No
contract, no container build. That is also the open half of #87.

## Things worth knowing before touching this code

- **A fixture shorter than production is how the two worst bugs of this session
  hid.** The receipt backfill lost all 9,883 observations to a project bucket
  71 bytes long against a 64-byte limit, because the test used a short id. The
  same shape recurred here: `TreeBatches` produced batches the server refused
  with `environment.schemaVersion must be 1, got 0`, and the leaf claim was
  silently never made because the lockfile fixture carried no registry artifact
  URL and no installed tree. Put the real thing through the real validator.
- **A test that passes can be measuring nothing.** Three did in one afternoon,
  all caught only by looking at what the run actually printed. A `cmd` quoting
  error meant the grandchild the test existed to catch was never spawned. A
  fixture whose outer script exited as soon as it had spawned meant the command
  SUCCEEDED before the deadline, so no timeout was exercised at all — `Run`
  returned exit 0 at two seconds and the assertion still passed. And an
  expectation that `npx` would be attributed to JavaScript was simply wrong
  about the code. Before trusting a green test on a bug you have not seen fail,
  break the fix and watch it go red.
- **The fake and PostgreSQL must not diverge**, and a green suite cannot show
  it. `dependency_edge` had no PG integration coverage at all before this
  session — the one row the whole dependency effort exists to create was
  untested in its production implementation.
- **Verify by rendering, not by reading.** The ad landed inside a finding card
  with the markup and CSS both exactly as written; only a screenshot showed it.
  The snippet relocates itself unless `[data-adisad-slot]` is present.
- **`.home-ad` is on a public ad-blocker filter list.** The home ad renders for
  visitors without a blocker and is hidden for those with one. Confirmed by
  control: `ad-banner`, `sponsored-content`, `adisad-unit` and
  `aria-label="Advertisement"` all render; only `home-ad` is hidden. Renaming
  it would work and would be circumventing a blocker the visitor installed —
  left as the user's call, still unanswered.
